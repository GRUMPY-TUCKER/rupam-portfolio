THINK IN
SYSTEMS.

A notification service is never just a send button. I start with the user promise, make the failure modes explicit, and design the smallest system that can keep that promise in production.

01 / CONSTRAINTS

What must be true?

Urgency, ordering, consent, cost, provider limits and data sensitivity shape the design before code does.

02 / CONTRACTS

Where is the boundary?

Clear event schemas, idempotency keys and ownership rules keep teams from coupling through assumptions.

03 / OPERATIONS

How do we recover?

Every alert needs an owner, every retry needs a limit, and every migration needs a reversible path.

We need email, SMS and push notifications. How would you make it reliable?
First, I would write down the user promise: accepted is not the same as delivered. Then I would map failure boundaries and let the API accept intent quickly while workers handle delivery.
R
HM
What happens when a provider times out or sends the same event twice?
Idempotent consumers, bounded retries and a dead-letter queue. The event contract carries an idempotency key, correlation ID and delivery deadline, so recovery is deliberate instead of mysterious.

And how would you know it is working in production?
Measure before guessing: structured logs, queue depth, provider latency and alertable SLOs. I would ship one provider behind a feature flag, replay realistic failures, and expand only when the runbook and rollback path are proven.
